# 歌里有我 产品需求与差异化方案

版本 v2 · 2026年9月29日 · 产品修订提案

## 1 本次修订结论

建议保留《歌里有我》的音乐记忆方向，以“听到这一段时，留住当时的自己；以后用一句经历找回来”为核心体验。将原 v1 的“公开故事语义检索”调整为“本人音乐记忆的找回”，公开共鸣作为经过单独验证后的扩展。

“歌曲时刻 × 人生时刻”可以保留为内容结构。对用户说“留住这一刻”“找回我的一刻”，对评委说明可验证的流程增量。默认私密、时间轴、歌词关联和自然语言搜索都有相邻产品先例，不能仅凭组合命名宣称独创。

本版本按用户价值、依赖关系和验证结果安排推进顺序，不以提交日期或假定开发人数裁剪产品。以下新增能力均为需求，当前实现状态见第 11 节。

### 1.1 最值得改变的三处

- **核心价值先在一个人身上成立。** 用户无需公开、不依赖陌生人供稿，也能保存、找回并重听自己的记忆。
- **让音乐位置真正参与体验。** 回看卡片后能回到对应录音版本的具体片段，才有机会比普通笔记更顺手。
- **给 AI 一个可检验的任务。** 从不完整或换了说法的经历线索中找出本人写过的记录，展示原文依据；不补写人生经历、不替用户解释情绪。

### 1.2 四个角色的判断

用户需要少填表、第一张卡就有用；评委需要看到与现有记录方式的操作差异；工程需要解决音源定位、权限、保存和检索；TME 的潜在价值在于用户从个人经历回到音乐播放。最后一项是产品假设，不能代替主办方诉求或增长数据。

## 2 证据边界与竞品对照

### 2.1 用户截图已经证明什么

COACH 活动介绍明确邀请用户围绕歌曲留下真实经历；投稿列表展示了歌曲、用户署名、文字、点赞和投稿入口。因此，“歌曲加个人故事”已发生直接重合。截图证明页面提供了这些能力的入口与呈现，尚不等于完整操作实测。[S1]

另一张截图还有“你的『九月』音乐记忆”。这足以否定“音乐记忆这个概念在 QQ 音乐不存在”的说法，但无法确认它是否保存用户主动书写的经历、是否支持某句歌词定位，以及活动结束后的管理方式。[S1]

| 对照对象 | 已有证据 | 对本项目的约束 |
|---|---|---|
| QQ 音乐 COACH 活动 | 歌曲关联用户文字、共同投稿、公开展示 [S1] | 不能主打“第一次让歌曲承载故事” |
| QQ 音乐月度音乐记忆 | 截图出现月度记忆入口，具体能力未实测 [S1] | 时间轴与长期回看不能直接写成独有 |
| Apple 手记 | 支持导入音乐并书写、回看和私人保存 [S2] | “音乐加私密日记”已有替代产品 |
| Last.fm | Scrobbling 记录听歌历史 [S3] | 区分播放轨迹与主动写下的生活经历 |
| Genius | 可点击歌词查看或贡献注释 [S4] | 逐句关联本身已有先例 |
| Music League | 围绕主题投稿歌曲、听歌和投票 [S5] | 主题只适合作为记录提示，不能充当主创新 |
| Spotify Prompted Playlist | 自然语言结合听歌历史等信息生成歌单 [S6] | 自然语言找音乐不是新概念；本项目拟检索个人记录 |

这些来源尚不能证明所有竞品都不具备拟议闭环。比较结论应写“本次证据所见的差异假设”，并用实测继续补全。

### 2.2 必做的一次 QQ 音乐对照实测

用当前版本和测试账号依次操作：选择指定录音版本与片段 → 留下一句仅本人可见的经历 → 退出后重新找回 → 换一种说法搜索 → 返回原片段 → 编辑或删除。再单独核实活动投稿、活动结束后回看、撤回和月度记忆入口。

记录平台与版本、日期、入口、点击数、是否完成、屏幕证据，以及“能力不存在”还是“本次未找到”。不要把未找到等同于不存在。若 QQ 音乐或现有替代工具已完整覆盖，比较完成效率和主观负担；没有实质优势时，调整核心问题，不用新名字维持差异主张。

P0 表示不解决就无法支撑核心主张；P1 表示会削弱价值或证据。此处是产品风险优先级。

| 级别 | 原依据或缺口 | 影响 | 本次修订 |
|---|---|---|---|
| P0 | v1 第11节已将平台功能缺失列为待核实；新截图显示重合 | 用“现有平台没有”参赛容易被反证 | 建立第2节证据矩阵与操作对照 |
| P0 | 提案用“双坐标”解释创新 | 描述了数据结构，未证明用户会记录 | 第4节定义真实触发、替代方式和行为验证 |
| P0 | v1 F06 将公开故事检索设为唯一 AI 核心 | 同时依赖作者供给、公开意愿和读者需求 | 先做本人记忆找回；公开共鸣另设门槛 |
| P0 | v1 F01 把歌词或时间点关联列为资源相关可选项 | 不能支撑“回到那一句”的核心演示 | 至少一条授权音源必须完成保存定位和重放 |
| P0 | 拟议私密体验沿用可切换的演示账号 | 演示权限不等于真实身份保护 | 真实用户测试前替换演示登录，先用虚构样例验收 |

| P1 | 默认私密卡片直接转公开 | 用户可能误发姓名、地点等原始细节 | 发布独立摘录，预览确认，与私人原文分离 |
| P1 | 原提案把“同一句歌”与“相近经历”连成一件事 | 文本相似不代表经历相同或愿意被联系 | 保留原文证据，避免共鸣百分比与身份推断 |
| P1 | README 仍称账号和数据库未接入 | 错估已有基础，也掩盖仍缺的写入闭环 | 按代码校正状态；不把已有模型当作完整功能 |

### 3.1 赛道建议的修正

暂保留“现有平台产品创新”的定位，原因是歌词页和播放器内的记录入口与 TME 使用场景相符。是否参赛合规仍以正式规则为准；现有截图展示用户价值、可行性、创新性三项，没有可据此引用的分值权重或“撞题即淘汰”规则。[S7]

独立 H5 只是演示载体，不自动等于独立产品赛道。也不能断言换到独立产品就必须自建曲库：外链回播放器等方式可能成立，但是否支持指定片段要另行核实。赛道选择应取决于实际产品边界和规则，不承担确保入选的承诺。

## 4 用户问题与路线选择

### 4.1 首要用户与场景

先验证有“把音乐与生活片段一起留下”习惯的听众：他们现在会截图歌词、收藏歌曲、发仅自己可见的动态或写笔记。演唱会散场仍是首个观察场景，也应观察后来重听时的需求，不能把一次演出后的热情当成长期使用证据。

用户任务：当一段歌让我想到具体的人或事时，我想用最少动作留下线索；以后看到这首歌，或只记得那段经历，也能找到记录并重听当时选中的片段。

现有替代是假设待访谈确认：收藏便于保存歌但未必保留生活线索；笔记能写经历但可能需要重新找歌、选版本和拖进度条。本项目应比较实际操作成本，而不是预设这些替代都不好用。

### 4.2 三条路线的选择

| 路线 | 有望解决的问题 | 最强反对理由 | 本次安排 |
|---|---|---|---|
| 公开故事加语义发现 | 从他人的经历发现音乐 | 与现有活动重合，依赖供稿和阅读两端 | 后续扩展，先验证公开意愿与阅读价值 |
| 私人音乐书签加经历找回 | 保存与回访具体音乐片段 | 少量记录时普通列表可能已足够；手记是强替代 | 推荐核心，与笔记和关键词检索直接比较 |
| 同一首歌的不同时期 | 看见自己随经历发生的变化 | 价值积累慢，不能靠几张假旧卡证明留存 | 作为核心记录的自然视图，不强做人生总结 |

推荐第二条，并让第三条增强回看体验。第一张卡应已经能编辑、重听和找回，不以积累大量数据为使用前提；记录少时优先呈现最近记录与歌曲分组，无需突出搜索框。

### 4.3 必须允许被推翻的假设

H1 用户愿意写一句线索，且记录步骤比现有方式更顺手。H2 重听原片段和原文能带来回访价值。H3 记录积累后，语义找回对模糊线索有额外帮助。H4 部分用户愿意主动发布摘录，另一些用户愿意因此进入音乐。H1–H3 是核心，H4 单独验证；任何一项都还不是已证实的用户事实。

## 5 核心体验与信息组织

### 5.1 保存一刻

从播放器或歌词页点击“留住这一刻”，自动带入当前歌曲版本和播放位置；输入一句经历，点击“只为我保存”。人生时间、标签、图片均不作为保存前置条件。没有具体片段也可只存歌曲，卡片明确显示“未标记片段”。

人生时间可填“毕业那年”“去年夏天”，也可稍后补充。创建时间由系统记录，不能代替经历发生时间。歌词定位不可用时使用时间点；歌词和音源都不可用时保留文字与歌曲信息，不能显示可用的片段播放按钮。

### 5.2 两种方式找回

入口一是歌曲：重听时看到“我曾在这里留过 2 段记忆”，按用户填写的经历时间查看；不确定时间单独展示。入口二是经历：输入“那次散场后，舍不得回家的夜晚”，在本人的记录中找出候选，显示自己的原话、歌曲版本和片段。

结果允许“不确定”或“没找到”。多个候选由用户选择，不让 AI 擅自认定“你说的就是这一次”。点“重听这一段”后定位播放；点“今天想补一句”可追加本人文字，同时保留旧记录。

### 5.3 公开共鸣的后续形态

在私人卡片上选择“分享其中一段”，编辑公开摘录并预览署名、歌曲及时间信息，确认后发布。私人原文、精确生活时间和其他未选择字段保持私有。公开页提供返回歌曲的入口；相近经历搜索只读公开摘录，显示可核对的原文。

允许取消发布，不要求公开才能继续使用。公开副本不会随着私人正文编辑而自动更新。公开能力上线前必须补齐举报、下架和基础内容处理；不引入点赞排名、私信或自动配对，避免给记录带来表演压力。

## 6 功能范围与验收要求

### 6.1 核心版本

以下是目标验收条件，不是当前完成情况。技术数值为拟定目标，需要实际测量。

| 编号 | 能力 | 最小可验收结果 |
|---|---|---|
| R01 | 片段选择 | 固定录音版本；保存合法时间点；重新打开后可定位；禁止跨版本套用偏移 |
| R02 | 私密记录 | 1–500字非空线索可保存；无标签、无人生日期也能成功；默认私密 |
| R03 | 持久化和管理 | 刷新与重新登录后可见；可编辑、删除；重复提交不会生成两张卡 |
| R04 | 我的记忆 | 最近记录、歌曲分组、关键词查询；同首歌可有多条记录，经历日期未知不伪排时间 |
| R05 | 经历找回 | 仅检索当前账号；返回至多3条候选和逐字可核对的本人原文；低置信度可无结果 |
| R06 | 重听片段 | 使用可播放音源真实定位，受控样例定位误差目标不超过1秒；资源失效显示原因 |
| R07 | 当时和现在 | 同首歌展示多段本人记录；追加文字显示新日期，不覆盖或自动改写旧文 |
| R08 | 身份与权限 | 真实登录后本人可读写；他人和游客不可访问私人列表、正文、搜索摘要及缓存 |
| R09 | 撤销与失败恢复 | 删除后立即不可检索、不可读；保存失败保留当前输入供重试；退出账号清除客户端私密状态 |

### 6.2 扩展版本

R10 独立公开摘录与撤回；R11 公开摘录的经历检索；R12 主题作为可跳过的写作提示；R13 用户选择的照片和音频补充。它们以核心价值和各自需求获得证据为启动条件。

自动听歌历史、情绪推断、AI 自传、复杂社交关系、跨平台曲库整合不属于当前核心承诺。即使开发资源充足，也先证明它们能改善用户任务，再增加复杂度。

### 6.3 关键状态

首次使用直接给“留下一刻”入口，不摆空洞的年度总结。保存中防重复点击，失败可重试。检索无结果提示换一个人物或事件线索，并保留普通列表；不生成一段不存在的记忆。模型超时切回关键词并标注当前方式。音源不可用时保留文字，说明只能回看；不把动画等同于播放成功。

## 7 页面和视觉的产品化

沿用已经选定的温暖、明亮、柔和方向与手写字体。首页五张卡和中央手机的大小、角度、相对位置遵循已确认参考，不再次重排。

| 页面 | 首要动作 | 信息与交互 |
|---|---|---|
| 首页 | 留下一刻 | 卡片连接歌曲或记忆；新用户展示明确标注的样例，老用户可展示本人内容 |
| 歌曲与片段 | 选择位置并记录 | 当前版本、歌词或时间轴；选中位置清楚可见 |
| 记录面板 | 只为我保存 | 一句经历为主要输入，时间和标签可展开补充 |
| 我的记忆 | 找回或重听 | 最近记录和歌曲分组优先；数据增加后提供自然语言检索 |
| 记忆详情 | 重听与补一句 | 本人原文、音乐位置、经历时间精度；编辑、删除及可选分享 |

动效用于表达“正在听”“已保存”“选中片段”。卡内微动和播放响应不改变外部几何布局；支持减少动态效果、键盘焦点与清晰对比。手写字体承担标题和情绪文案，长正文及表单以易读为先。首页成功指标是进入记录或找回任务，而非动画观看时长。

## 8 数据和权限设计

沿用现有用户、歌曲、MemoryCard 和 Tag 模型，新增内容通过迁移实现，保留旧记录。

| 数据对象 | 建议字段或规则 | 解决的问题 |
|---|---|---|
| Song 或 Recording | 现有 song_id 和 version；补充稳定来源标识、时长、播放能力 | 明确是哪一个录音；曲目同名不意味着时间点相同 |
| 音乐锚点 | anchor_type 为 song、time 或 lyric；offset_ms 可空；歌词版本与行标识可空 | 无歌词仍可定位；修改音源时验证锚点，失效需重选 |
| 人生时间 | 原始 life_time 保留；可空起止日期与 precision 为 day、month、year、range、unknown | 保留模糊表达，禁止 AI 捏造精确日期 |
| MemoryCard | owner_id、story、锚点、created_at、updated_at、revision、deleted_at | 内容版本、编辑冲突和删除状态可追踪 |
| 回看补充 | memory_id、作者本人、追加原文、追加时间 | 保留当时与现在，避免模型改写旧记忆 |
| 检索索引 | owner_id、memory_id、revision、处理授权状态；不另造故事正文 | 索引过期可丢弃，返回前再次查权限和版本 |
| 公开摘录 | 独立 id、关联卡片、选定文字、展示字段、发布与撤回状态 | 私人编辑不自动扩大公开范围 |

所有私人读写和检索的身份来自服务端会话，不信任客户端传入的 owner_id。召回前按所有者限制，返回前再检查记录是否存在、权限与版本是否仍有效。日志、异常信息和查询缓存不得保存可被其他用户读到的完整私人正文。

删除或撤回首先在数据库生效并阻断读取，再异步清理向量与缓存；清理失败可重试，但不能继续返回内容。公开摘录撤回不会删除私人原文；删除原卡同时撤回关联摘录。现有公开种子数据应显式迁移为样例摘录，不自动把历史私密记录公开。

若个人语义检索需要外部模型处理正文，启用前清楚说明处理范围与用途，由用户选择；不启用仍可保存、回看与关键词搜索。不同用户数据不能混入同一无权限约束的检索池。没有端到端加密实现时，不使用相应隐私宣传。

## 9 AI 的必要性与检索边界

### 9.1 具体任务

AI 帮助理解线索与原文之间的表达差异，例如用户查询“离开校园后的第一晚”，候选原文写“毕业后搬进出租屋，第一次自己关灯”。结果必须展示原文并让用户确认。此例是设计样例，不是真实用户数据。

实现可从普通全文检索开始，增加语义召回与重排作为可替换层；以同一授权语料比较效果后决定模型和检索方案。返回 memory_id、revision、evidence_span、匹配类别及必要的澄清提示。证据片段应从原文截取并校验，不能由模型自由补写。

查询中的否定、人物关系、时间、地点是约束而不只是关键词。不得把“一个人搬家”与“陪朋友搬家”解释成同一次经历；不得从文字推断诊断、人格或与他人的关系。公开检索与“我的记忆”入口分开，不混合展示权限来源不同的内容。

### 9.2 AI 不一定值得进入核心

如果在真实记录规模上，关键词、歌曲分组和时间筛选已能同样快地找回，就应降低 AI 的产品权重。若语义检索不能稳定优于这个强基线，本项目的 AI 创新主张仍未成立；不能以聊天界面、生成文案或虚构大语料补足展示。

## 10 验证计划与决策门槛

### 10.1 用户价值验证

先访谈 8–12 位有实际记录行为的听众，要求回顾最近一次事件并展示自愿提供的记录方式。不要只问“你会不会用”。观察记录触发、为什么没记、多久回看以及找不到时如何处理；招募量是研究计划，不是已有样本。

让同一位参与者用其熟悉的替代工具和本产品完成等价保存与找回任务，交替顺序。分别记录写字时间与操作时间、完成率、错误次数、找回耗时和主观负担。不要要求所有人写同样长的故事，或把引导后的任务成功当成自然需求。

随后观察自发的再次记录、回访旧卡和重听片段。统计完整观察周期内有机会遇到触发事件的用户，并同时报告总人数、失访与零使用；不以提醒后的点击替代自然回访。

### 10.2 检索和权限评测

| 项目 | 方法 | 拟定验收与决策 |
|---|---|---|
| 基线对照 | 同一可访问语料，对比关键词加歌曲/时间筛选与语义方案 | 报告 Top3 正确率和完成时间；无稳定增益就弱化 AI 主张 |
| 查询覆盖 | 至少50条保留查询，含改写、人物、否定、时间、相似事件和无结果 | 开发与评测查询分开；候选由记录者确认，另做独立复核 |
| 证据忠实 | 校验每条返回摘录是否来自指定版本原文 | 测试集中编造原文为0；一例失败即修复 |
| 无结果 | 确保语料中确无答案；检查是否强行返回高置信候选 | 单独报告误命中率，不只报命中题正确率 |
| 访问隔离 | A、B、游客、过期会话；篡改 id；删除后重搜；模拟旧缓存 | 任一越权内容、片段或摘要泄露均阻断发布 |
| 延迟和成本 | 在相同设备/网络与数据规模下测量；区分冷启动和热请求 | 交互目标检索 p95 不超过3秒；5秒超时降级；公布样本量与单次成本 |

受控合成语料可以验证权限、边界和算法，但必须标注；它不能证明真实用户需要语义找回。检索正确率不能单独决定产品成败，还要看用户是否愿意留下和再次使用记录。

### 10.3 公开共鸣的启动条件

只有当私人使用已出现自然回访，再验证“愿意发布摘录”与“愿意读并播放关联歌曲”这两个独立行为。主题提示可辅助招募，不将运营供稿量当作产品自增长。公开量不足时保留私人工具价值，不制造看似真实的社区繁荣。

## 12 演示与评分维度

### 12.1 两分钟主路径

| 时间 | 操作 | 必须看到的证据 |
|---|---|---|
| 0–15秒 | 说明“记得那段经历，想重听当时留住的片段” | 一句话用户任务，明确演示账号与样例 |
| 15–40秒 | 在指定版本选择片段，写一句线索并私密保存 | 真实写入、保存成功、默认私密 |
| 40–55秒 | 刷新后从我的记忆打开 | 持久化，原文和位置一致 |
| 55–85秒 | 用不同表述查询本人记忆 | 真实检索、原文依据；旁示同语料基线结果 |
| 85–110秒 | 点击候选并重听片段 | 正确录音和真实音频定位，原文同步可见 |
| 110–120秒 | 展示可补充的本人记录，并总结 | 从保存到重听已闭环；长期价值仍待观察 |

另备独立验收演示：切换身份不可读、无结果、模型超时、删除后重搜。公开分享如果已经实现，可以单独演示；主路径不依赖发布与陌生人供稿。

### 12.2 演示真实性

允许使用标注为虚构的生活样例、授权测试音乐和预先录入的历史卡片；日期必须说明为样例。保存、权限、检索和音频定位必须真实运行。预计算索引要说明，录屏回放要标注，不能把预设答案称为现场 AI 检索。

若只有歌曲信息没有可播放音源，可以展示记录与检索流程，但必须承认核心“回到片段”尚未证明。若尚未接入 TME，展示拟议入口图与独立 H5，并明确两者关系，不伪装真实平台能力。

### 12.3 与三项评分维度对应

| 维度 | 本项目拟证明的增量 | 应提交的证据 |
|---|---|---|
| 用户价值 | 保存更顺手；生活线索能帮助回访音乐 | 与实际替代方案的任务对照、自然回访记录 |
| 可行性 | 从记录到检索再到片段重听可完整操作 | 可运行闭环、异常路径、权限测试、实际资源边界 |
| 创新性 | 在听歌场景将个人线索、原文找回和精确重听连成体验 | 竞品逐项对照、AI 与强基线的同语料实验 |

建议投稿表述：“《歌里有我》让听众在一段音乐里留下自己的生活线索，以后从歌曲或一句经历找回本人原文，并重听当时标记的片段。”这是一项待体验与数据证明的组合创新，不宣称技术壁垒或平台首创。
